## Blocking findings

All four are fixed. Each entry records the defect as found, and the fix that closed it.

### B-1 (Critical) - a `bye` can move `activeOwner`, and the spec mandates that it does

**Where:** `wire-format.md` "Ingress order" final line, `design.md` §7.1 and §5.4,
`adr/0016`.

`wire-format.md` ends ingress with "Only then is the datagram processed by §5.4's
convergence rules" - unconditionally, for every accepted datagram. A `bye` carries `seq`
and `activeOwner` like any other datagram. So a departing machine whose `seq` is the latest
sends `bye: true` with `activeOwner = self`; the receiver runs §5.4, sees
`peerSeq > localSeq`, and adopts `activeOwner = departing machine`, then clears presence.

ADR 0016's "a `bye` **never alters `activeOwner`**" is sender discipline that the receiver
pipeline does not enforce. `design.md` §10's row asserting a `bye` "leaves `activeOwner`
untouched" therefore contradicts §7.1's ingress order in the same document set.

**Why it matters:** violates §5.2 - "Peer appearing or disappearing ... never alters
`activeOwner`" - which §5.2 itself calls "the central property of the design". The victim
holds `activeOwner = <absent peer>` and mutes the instant that peer returns. Ownership
moved by a departure, with no deliberate event, violating Goal 5.

### B-2 (Critical) - a `bye` can re-open the lid-open defect §7.6 exists to fix

**Where:** `adr/0016` Consequences, `design.md` §7.6 and §7.1.

§7.6 makes quarantine's outcome depend on presence: "If the peer is observed during the
window, the peer's `(activeOwner, seq)` is adopted regardless of `seq` ordering. If the
window expires **with no peer**, the machine resumes normally from persisted state." A
`bye` "clears peer presence immediately".

So a `bye` can clear an observation that had already legitimately happened. The laptop
wakes and enters its 12s window; it sees the desktop's heartbeats and should defer to the
desktop's state; the desktop then shuts down and sends its `bye`; the laptop's window now
expires "with no peer" and it asserts its stale persisted ownership instead. The desktop
returns, sees the higher `seq`, adopts, and mutes.

**This requires no attacker.** An ordinary shutdown during an ordinary resume produces it.

**On the "forged" framing.** ADR 0016 claims a forged `bye` is harmless because it only
unmutes. Forgery is not a real concern - every datagram is HMAC-SHA256 keyed by `pairKey`,
which never crosses the network. Replay needs no key and §7.1 already accepts it
explicitly. The reviewer's observation that `bye` gives a replay the new power to *clear*
presence rather than only *extend* it is correct, but once B-2 is fixed the consequence is
bounded to an unmute, which is Goal 1's safe direction. ADR 0016's claim was premature
rather than wrong.

### B-3 (Critical) - the recovery script destroys the recovery record

**Where:** `scripts/uninstall.ps1` steps 2-5, `src/SoloSpeaker.App/Program.cs`,
`README.md` "Building", `implementation-plan.md` §6.5.

If `& $targetExe '--restore'` exits non-zero, `uninstall.ps1` prints two warnings, sets
`$restored = $false`, and then **proceeds unconditionally**: step 4 deletes the binary,
step 5 deletes `%LOCALAPPDATA%\SoloSpeaker`, which is where §7.3 puts `ledger.json`.
Endpoint still muted, ledger gone, binary gone, `--restore` impossible.

A non-zero exit is not exotic - `implementation-plan.md` §4.5 and matrix rows E5, E7 and E9
enumerate corrupt-ledger, enumeration-failure and mutex-held as anticipated non-zero exits.
**With the committed scaffold it happens every time**, because `Program.cs` `Main` ends
`return args.Length;` and `--restore` is one argument.

**Why it matters:** this is the Goal 1 strand - "No reachable state leaves a machine muted
with nothing running to unmute it." `README.md` asserts uninstall "runs `--restore` before
deleting the binary, so an endpoint this app muted can never be stranded by an uninstall",
which the script's own `else` branch falsifies. It ships in the CI artifact today.

**Coupled defect (High).** `CloseMainWindow()` cannot stop a tray app: `MainWindowHandle`
is zero for a process with no visible top-level window, so the call returns `false` having
sent nothing. `uninstall.ps1` discards `WaitForExit`'s result and proceeds against a live
instance; `install.ps1` checks it and throws, which means it throws on **every** upgrade
over a running instance, so matrix row G7 can never pass. Both scripts' central premise -
"stop it first and let its graceful-exit path restore audio and clear the ledger" - is
inoperative.

### B-4 (Critical / High) - nothing in `SoloSpeaker.App` is testable

**Where:** `SoloSpeaker.slnx`, `tests/SoloSpeaker.Core.Tests`, `implementation-plan.md`
§4.1 and §4.5, `AGENTS.md` §3.

The only test project targets `net10.0` and therefore cannot reference `SoloSpeaker.App`
(`net10.0-windows`). But `implementation-plan.md` §4.1 claims CI can prove "ledger replay
and its failure modes; atomic state writes", and §4.5 lists seven such cases. Those
implementations live in App: file paths, JSON shape, `File.Replace` sequencing, and DPAPI.
`AGENTS.md` §3 has now codified the layout including the absence.

**Root cause.** `IMuteActuator` fuses two components that `design.md` §6 and `AGENTS.md` §3
both name separately - `MuteActuator` and `Ledger`. §3 says "New code goes in the component
it belongs to; do not invent a parallel decomposition," and the fused interface is exactly
that. Separately, the **roster has no seam at all**, despite being the right-hand side of
§5.5's predicate, the most load-bearing line in the repository.

**Why the timing matters:** once work item 5 writes JSON inside App and work item 7 puts
replay behind the actuator, redrawing the seam stops being a refactor and becomes a
rewrite.

## Approved remediation plan - LANDED

Approved 2026-09-28 and executed the same day. All four fixes are in; `design.md` is at
revision 4. The subsections below are kept as the record of what was changed and why.

Verification: full `AGENTS.md` §7 sweep green, and the Goal 1 branch of `uninstall.ps1`
exercised against a stub that exits non-zero - binary and `ledger.json` both survived, exit
code 1. The happy path was checked separately to confirm removal still works.

### Fix 1 - `bye` bypasses convergence (closes B-1)

State normatively that a datagram with `bye: true` is consumed by the presence layer
**only** and never reaches §5.4. Its `seq` and `activeOwner` are still signed -
canonicalization rule 9 forbids omitting fields - but are ignored on receipt, in both
directions of `seq` ordering.

Sender ordering is part of the contract: a claim broadcasts its state datagram first, per
§7.1's "immediate extra send on any state change", and only then the three `bye`s. If the
state datagram is lost and only the `bye` lands, the claim is lost and ownership stays put.
That is correct under §5.2 and identical to what happens if the machine simply dies.

Files: `design.md` §5.4 and §7.1, `wire-format.md` ingress and Departure, `adr/0016`.

*Rejected alternative:* forbid `bye: true` on a datagram whose `seq` exceeds the sender's
last broadcast. This is a sender-side rule requiring receiver-side validation to mean
anything, which is the shape of the original bug.

### Fix 2 - quarantine observation becomes a latch (closes B-2)

§7.6's "if the peer is observed during the window" becomes a **latch**, set by any accepted
non-`bye` datagram at any point in the window and readable at expiry. It is not the
instantaneous presence flag, and a `bye` cannot clear it.

This also closes the presence re-acquisition gap that no document specified: a `bye` clears
presence and sets a departed flag; presence is re-established by the next accepted
non-`bye` datagram.

**No anti-replay rule.** Considered and deliberately dropped. Once the latch is in, the
worst a replayed `bye` achieves is clearing presence, which unmutes - Goal 1's safe
direction - plus oscillation under sustained replay. Both are within the tolerance §7.1
already grants replay. A `seq` gate would add mechanism to a frozen wire format's semantics
to defend against a threat the design deliberately accepts, on a home LAN, for a
two-machine personal tool.

Files: `design.md` §7.6 and §7.1, `wire-format.md`, `adr/0016`.

### Fix 3 - the uninstall strand (closes B-3)

- `Program.cs`: return `0` for a bare launch and a documented non-zero for any argument,
  with a message naming it unimplemented. Returning `0` would be worse than the current
  bug - `--restore` genuinely cannot restore anything yet, so claiming success is the
  dangerous direction.
- `uninstall.ps1`: gate deletion of the binary **and** of `%LOCALAPPDATA%\SoloSpeaker` on
  `$restored`. On failure, leave both in place, exit non-zero, and tell the user to fix and
  re-run. Separate `-KeepConfig` from ledger retention, which one switch currently
  conflates.
- Both scripts: check `WaitForExit`'s return value and abort loudly when the process is
  still alive.
- Record a real shutdown channel - a `--shutdown` switch or a named event - as a
  requirement of work item 12. It cannot be built before the app exists.

### Fix 4 - redraw two seams (closes B-4)

- Split `ILedger` out of `IMuteActuator` and `IConfigStore` out of `IStateStore`, matching
  the component list `design.md` §6 and `AGENTS.md` §3 already declare binding.
- Add `IFileStore` (read, write-atomic, delete) so ledger replay and atomic-write *policy*
  live in Core, leaving App with thin `File.*` calls plus the DPAPI wrapper.
- Add `tests/SoloSpeaker.App.Tests` targeting `net10.0-windows` for what genuinely cannot
  move: DPAPI profile binding and the icon-resource assertion.
- Update `AGENTS.md` §3 and `implementation-plan.md` §3 to match.

### Verification

Full `AGENTS.md` §7 sweep, plus one behavioural test rather than an argument: run
`uninstall.ps1 -InstallRoot <temp>` against a stub that exits non-zero and confirm the
binary and `ledger.json` both survive. That is the Goal 1 branch.

Add `design.md` §10 rows for the `bye` bypass, the quarantine latch, and presence
re-acquisition, per `AGENTS.md` §5. Add matching manual matrix rows for the replay-flood
case that row F7 currently misses.

`design.md` goes to **revision 4** when this lands.

## What held up

Recorded so it is not re-litigated. All three reviewers converged on these.

- **§5.5's positive predicate.** The attack reviewer tried to reach a both-muted state
  through a corrupt `activeOwner`, an asymmetric roster, a retired machine, and
  pairing-mode enrollment. The positive form held every time. This is the most load-bearing
  line in the repository and the revision-2 fix for the revision-1 Critical is correct.
- **The `seq` delta bound.** Right shape, right place - at ingress, before processing - and
  it genuinely defuses the `uint64.Max` pin.
- **`pairKey` handling end to end.** `.gitignore`, ADR 0013's field-scoped DPAPI, ADR
  0015's logging prohibition, `AGENTS.md` §6, and ADR 0011's delete-on-both-sides are
  consistent. Deriving the DPAPI entropy from `pairId` was singled out as a good detail.
  The revision-1 key-derivation Critical is properly dead.
- **The phase re-cut.** Everything touching the wire landing in phase 1 is right, and ADR
  0016's now-or-never framing is correct **as framing** - the objection was to the field's
  semantics, not its timing.
- **The split mic signal (ADR 0009)** and its asymmetric error costs.
- **`install.ps1`'s Task Scheduler reasoning.** The audio-service race at logon is real and
  the delay is the right mitigation. `asInvoker` and the hotkey rationale are also correct.
- **`IClock` splitting wall-clock from monotonic time**, which is correct specifically
  because §7.6 is about resume-from-sleep, where wall clock jumps and monotonic does not.
- **The platform-neutral `net10.0` target for Core.** Called the single best structural
  choice in the repository - the only compiler-enforced constraint here. Note the honest
  bound: it prevents referencing Windows types, but not `DateTime.UtcNow`, `File`,
  `Socket`, or `Random`. It does less than `implementation-plan.md` §2 claims, and is still
  worth keeping.
- **`manual-test-matrix.md`**, described by the attack reviewer as the best document in the
  set. Its weakness is that it faithfully tests behaviours the specs have not pinned down.
